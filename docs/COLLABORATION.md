# 跨设备与两人协作

本阶段分支、各自任务和接手步骤见 [当前双人开发交接](COLLABORATION_HANDOFF.md)。

## 分工

- 米老师负责审计业务逻辑、原表格式、底稿和报告规则，可在自己的任务分支提交代码，并负责业务验收。
- 产品负责人负责应用功能、组织权限、设备、订阅、官网、视觉和运营安排，负责协调整体实现、技术测试和版本合并。
- 后续同事：使用自己的账号加入。现阶段没有完整团队名单，不能编造姓名或权限。

## 固定节奏

**Issue 说清楚 → 开分支 → 修改 → 测试 → PR → 业务验收 → 合并 → 另行发布。**

每次只做已点名的修改。Issue 写「只改哪里、不改哪里」，PR 必须逐项回应。米老师验收后留言“本项通过/未通过及原因”，开发者不要把其他反馈混进来改。

## 同一人换电脑

旧电脑：保存文件 → 在自己的工作分支 Commit → Push → 在 Issue 写交接：分支、提交号、完成内容、待办和测试结果。**本地 Commit 但没 Push，另一台电脑收不到。**

新电脑：用自己的账号克隆同一个私有仓库 → Fetch → 切换同一工作分支 → Pull → `npm ci --ignore-scripts` → 运行。开始修改前确认上一台电脑确实推送成功。

回到旧电脑也先保存/提交本地未完成工作，再 Fetch/Pull；不要直接用新电脑文件覆盖旧目录。`node_modules`、环境配置和浏览器数据不在同步范围。

## 两人同时开发

不同任务使用不同分支。可能修改同一文件时，先在 Issue 留言认领/协调。不要同时直接修改 main。出现冲突先暂停，保留双方修改，由了解代码的人解决；米老师无需选择“全部用我的/全部用对方的”。

## 三个容易混淆的同步

| 对象 | 如何同步 | 本仓库能否自动做到 |
|---|---|---|
| 源码、开发文档 | Git commit / push / pull | 可以 |
| 线上软件版本 | 负责人构建并发布 | 不会因GitHub合并自动发布 |
| 客户项目、资料和附件 | 授权的业务备份/迁移 | 当前不会自动跨设备同步 |

不要把客户账表/底稿发到 GitHub Issues。当前浏览器本机冻结也不等于服务端不可篡改归档；正式多人业务协同要单独设计鉴权、权限、存储隔离、版本锁及审计留痕。

## 邀请与权限（负责人执行）

仓库 Settings → Collaborators / Manage access，邀请米老师的 GitHub 用户名。**新建仓库并不等于已邀请成功**；以对方接受邀请、能看见 Private 仓库为准。个人私有仓库的角色能力受 GitHub 当前方案限制；邀请前确认授权范围。不要共享 owner 登录或让她提供密码。

分支保护/Ruleset 取决于账号方案和仓库能力。本次文档约定 PR 流程，不把“写了 CODEOWNERS”冒称已强制保护；实际设置及是否生效应另行验证后记录。

## 一条交接示例

```text
任务：#12 合同下载
分支：fix/12-contract-download
提交：填写实际SHA
已做：修复点击无响应；只填明确乙方字段
未做：不改条款、不填未知银行账户
测试：填写真实通过/失败/跳过数
待米老师验收：用获准的脱敏模板检查版式和字段
发布：尚未发布
```
