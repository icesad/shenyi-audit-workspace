# M2：员工定向邀请与本人激活

日期：2026-11-15；分支`codex/employee-invitation-activation`，接续`04a014b`。这是隔离的合成研发候选，不是正式员工或短信服务已经开通。完整接续记录见[进度](../进度.md)，身份主线见[手机号与微信](PHONE_WECHAT_AUTH_PLAN.md)。

## 使用流程

1. 当前团队的项目经理或合伙人另有有效`member.invite`授权，或[人工审核开通](MANUAL_TEAM_ONBOARDING.md)的独立技术管理员，才能展开“员工邀请”。两个来源分别核对；职级高不自动获得该授权，实习生/助理即使误授业务或技术grant也拒绝邀请管理。
2. 管理员填写受邀手机号，只能选择实习生或助理。邀请码创建后显示一次，关闭面板、切换团队或退出即清除；列表只显示脱敏手机号、岗位、期限与状态。软件不发送消息或自动操作剪贴板，管理员自行转交的动作不属于本轮自动执行。
3. 受邀人退出当前账号后展开“受邀激活账号”，核对邀请码、手机号、目标团队和岗位，获取本人短信验证码。新账号自行填写姓名及密码；已有手机号账号填写当前密码，不能用短信重置原密码或名称。
4. 本人明确勾选加入团队/岗位后激活。成功不会自动发放会话，需另用手机号和密码登录。新成员没有自动指派任务、项目读取、附件或邀请权限；具体资料仍需后续明确指派。
5. 已发出的邀请可以撤销。邀请人被禁用、降职、失去邀请授权、团队停用、邀请过期或已消费时，未完成的预览/发码/激活均拒绝。

尚未配置短信供应商时，界面显示验证服务「尚未开通」。在有效试点或订阅中，创建邀请会预留一席。员工本人激活后，预留席位改计入已启用人数，应用也会提示后续登录步骤。

## 创建应答丢失后核对

新版桌面和服务端配合时，创建前生成一个请求编号。若应答未收到，恢复连接后在原团队的「员工邀请」中点「核对本次邀请」。应用先核对当前邀请权限，再按编号只读查找本次记录。请以核对结果和「订阅与席位」中的预留数为准。

| 核对结果 | 下一步 |
|---|---|
| 已查到待激活记录 | 如果员工手里仍有可用的原邀请码，请其按原流程激活。原码遗失或未收到时，先与员工确认尚未激活，再撤销核对出来的这一条。确认撤销、席位释放后，可创建新邀请。 |
| 暂未查到记录 | 可按界面提示重填原手机号和岗位后提交。桌面沿用这一次的编号。若第一次请求随后落库，重复提交会指向既有结果，同一请求只预留一席。 |
| 已使用、已撤销或已过期 | 按显示状态办理。已使用的邀请对应员工的现有账号；已撤销或已过期的预留按原席位规则处理。 |

如果邀请码已经显示而邀请列表暂未刷新，先核对并转交当前显示的凭据，再刷新记录。退出账号或重新打开客户端后，在原团队查阅近期邀请及席位。找到多条相同遮罩的记录时，先核对准确的邀请状态和实际领用人，再决定撤销哪一条。

## 接口和数据边界

| 入口 | 行为 |
|---|---|
| `GET /api/auth/onboarding/capabilities` | `{available,invitationOnly:true}`；不改变既有`/api/auth/methods`形状，无供应商秘密 |
| `GET /api/teams/:teamId/employee-invitations/access` | 有效成员的当前邀请能力；UI读取此结果，不用前端角色值代替权限 |
| `POST /api/teams/:teamId/employee-invitations` | 生成随机32字节邀请码，仅存SHA-256；固定目标手机号及intern/assistant，测试期限24小时 |
| `GET`同路径 | 每页最多50条，可前后翻查历史；脱敏手机号、角色、期限、状态，不再返回邀请码；见[分页合同](EMPLOYEE_INVITATION_PAGING_CONTRACT.md) |
| `GET`同路径并指定 `requestId` | 仅在当前获授权的原操作者和团队范围内核对该次创建，返回零条或一条同样的脱敏记录。 |
| `POST /api/teams/:teamId/employee-invitations/:id/revoke` | 再次校验当前角色和独立权限；撤销并使未消费激活挑战失败 |
| `POST /api/auth/onboarding/preview` | 精确邀请码＋手机号才返回最小团队/岗位/脱敏手机号/期限，不说明账号是否存在 |
| `POST /api/auth/onboarding/challenges` | 服务端SMS适配器、activate专用挑战；5分钟且不晚于邀请到期，绑定目的/邀请/手机号/期限的HMAC，无明文code落库 |
| `POST /api/auth/onboarding/activate` | 本人code＋密码＋`accept:true`；原子建立/复用身份、加入指定低权限角色并消费挑战和邀请；只返回`{activated:true}` |

发送复用既有全局与手机号限流桶，再限制单邀请；验证最多5次，尝试计数在异步密码计算前提交，失败不退还。SMS返回后、密码计算后重新读取邀请人/团队/角色/grant、邀请/挑战期限及消费状态。服务商错误转换为固定通用503，不能把供应商秘密或异常直接显示。

带 `requestId` 的创建在同一事务内核对已有操作并预留席位。同一账号和团队重复提交该编号时，服务端返回已记录的冲突状态，原邀请码仍只随首次创建成功应答返回。变更邀请的岗位或手机号时，需要按原记录状态处理后使用新编号。历史客户端使用原有创建和分页接口。

新账号使用内部UUID和随机内部username、异步scrypt及已验证手机号映射。已有账号只有在当前密码正确、账号/手机号/凭据版本仍有效，且没有任何团队成员记录时才可复用；不覆盖姓名、密码、禁用状态或既有角色。手机号在计算期间新出现归属也拒绝，不自动合并账号。账号、凭据、手机号、成员、邀请消费、挑战消费和活动留痕同事务，存储失败不留孤儿账号。

当前对“已有任意业务或技术归属记录（含停用/撤销）”保守拒绝新增归属；这是多团队、离职转所及所有权政策未确认前的实验限制，不是已批准的商业规则。人工开通候选已实现首管理员，真实团队/主体核验、所有权转移和恢复仍待完成。不会把团队名称或ID当成已核实的机构身份。

技术管理员的员工票据及挑战新增独立表，避免旧业务邀请的membership外键迫使技术账号获得审计职级。相同API只由服务端可信source选择表；列表按[分页合同](EMPLOYEE_INVITATION_PAGING_CONTRACT.md)跨来源稳定排序、每页最多50，明文票只创建时返回。旧业务票仍依赖原经理/合伙人授权，新technical授权不能救活已降职票据；跨source出现歧义拒绝。

`activation-schema.sql`只给标记正确的M2隔离库增加两张表，不改既有SMS用途CHECK、旧平台或客户库。升级共享合成库前已做SQLite在线备份；禁止将该脚本当作正式数据库迁移包。

## 桌面和取消语义

桌面增加8个窄操作，总计24项IPC；没有原始网络、文件路径或任意权限参数。会话token仍在主进程，邀请列表字段白名单投影；邀请码是管理员明确需要转交的一次性信息，允许当次展示，不是可以持久化的登录会话。换团队、退出、401、关闭面板时立即清除，迟到响应不得恢复旧账号的代码或列表。

受邀人修改邀请码/手机号、切换登录方式、开始微信或返回登录时，清除预览、验证码、密码和勾选。界面只在看到真实服务能力后启用发码；核对目标和明确同意是提交前提。异步原生`details`打开事件保留用户刚输入的内容；关闭/身份变化仍清理。

激活提交是一次原子写入，当前没有服务端取消端点。提交后返回登录仅清除本地输入并忽略迟到界面结果，可能已经完成激活；界面会提示可用手机号登录核对，不能承诺服务端回滚。不要将此行为等同于微信待完成事务的取消。
