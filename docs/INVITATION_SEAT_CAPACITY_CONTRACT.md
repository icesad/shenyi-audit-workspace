# 团队席位容量与邀请预留

2026-11-18，M5E 服务端候选。已确认的产品决定见[订阅与席位决策](SUBSCRIPTION_SEAT_DECISION.md)。

启用且具备业务资格的成员各占一席，纯技术管理员不占席。三类员工邀请从发出起分别预留一席，包括旧式用户名邀请、经理或合伙人发的手机号邀请、技术管理员发的手机号邀请。接受邀请时在同一事务内释放该预留并增加一个启用成员。撤回或达到邀请到期时刻即释放预留。旧式用户名邀请没有撤回接口，按接受或到期释放。发邀请的人失去权限后，原规则会阻止激活，预留保留至撤回或到期，避免资格恢复时超额。

已购容量是本团队有效容量记录的数量之和，区间为含起点、不含终点。可用数为已购容量减启用占席和待用邀请预留，最低显示为零。容量不足阻止新增邀请、激活及新增兼任占席。已启用成员保留原业务权限，原订阅到期规则继续执行。成员停用或撤销兼任释放占席，在位成员换职级不重复计席。同一团队的申请在 SQLite 写事务中串行检查，订阅、容量及邀请期限在最后一次发布检查共用服务端时刻。

内部容量记录表只追加，按团队隔离。相同操作编号和内容重试返回原记录，异内容冲突。数据库初始化不自动配置容量。没有 HTTP 授予容量的入口。本轮通过可信内部接口写入合成容量；年续费订单只兑现期限，容量记录的期限不会由该订单隐式延长。

服务端显式开启 `invitation-reservations-v1` 后执行容量规则，要求严格设备证明和 `team-management-v1`。本团队技术管理员可查询 `GET /api/teams/:teamId/billing/seats`，返回购买数、启用数、预留数、已承诺数和可用数。查询沿用当前会话、已绑定设备和技术管理员资格，且不提供人员名册或审计内容。容量状态和邀请发出权限分别按原授权执行。

增购席位与团队原到期日对齐并按剩余期限折算。订单、精确折算口径、正式价格、兑现及桌面购买流程在后续开发。当前候选只验证了容量、预留和许可入口。
