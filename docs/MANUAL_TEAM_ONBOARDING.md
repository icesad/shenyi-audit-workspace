# 团队人工开通与首管理员

日期：2026-11-15。已确认产品决定：前期由产品负责人（当前用户）人工审核开通团队和首管理员，员工通过邀请激活。本文记录 M2 本机隔离候选；不代表真实主体审核、生产账号开通或商业订阅已经上线。

## 使用流程

1. 产品负责人核对团队及指定首管理员资料，在独立获授权的审核账号中录入团队名称和手机号。此时只生成待审记录，不创建团队。
2. 核对后填写审核账号当前密码，选择批准或拒绝。批准生成一次性首管理员邀请码，列表不再返回它，关闭面板或退出即清除。需人工转交给指定本人，软件不代发消息。
3. 首管理员在登录页的“首管理员激活”中输入专用邀请码和指定手机号，核对团队，完成手机号验证码和密码确认，明确接受管理责任。
4. 验证成功才原子创建团队和技术管理员。不会自动登录、赋予审计职级或开放资料。新账号本人设密；已有已验证手机号的孤立账号须验证其当前密码，保留原身份与密码。
5. 获准试点的团队由产品负责人另行审批期限和席位。首技术管理员使用手机号＋密码登录并绑定设备，在试点有效期和席位余量内可发员工邀请。员工本人验证激活后须由有权人员另行指派项目和任务。

## 受管服务首个试点

发放首管理员凭据前，由部署人员用本次受管服务配置执行 `--check-pilot-readiness`，记录 `pilot-ready` 回执。随后在获准环境验收实际短信激活和本次试点授权。 [首队试点就绪检查](MANAGED_TEAM_SERVICE.md#首队试点就绪检查)

产品负责人在已绑定的客户端打开「人工审核开通团队」，找到首管理员已激活且领取首个期限前的团队。在对应申请行填写北京时间的结束日期及时间、席位上限，在审核密码框输入当前密码，再点「批准试点」。初始产品负责人具有独立的试点审核权。团队开通审核权单独授予时，仍需此试点审核权才能批准。

开通申请按录入时间倒序显示，每页最多 50 条。较早的申请可用「下一页」查找。同页审核完成后，可在该页核对更新；点击「刷新审核记录」回到最新一页。翻页及手动刷新会清除审核密码和当前显示的首管理员邀请码，操作前请先转交仍需使用的凭据。

服务端从批准提交时开始试点。结束时刻和席位上限按申请逐队登记。试点、首个期限和席位在同一事务提交，重复确认相同审批只返回原回执。已有期限或容量的团队使用原有权益。试点到期后，邀请和业务新增按既有到期规则处理。团队技术管理员可在「订阅与席位」查看试点。 [试点与正式收费决定](SUBSCRIPTION_SEAT_DECISION.md#28-首队试点和正式收款入口)

邀请一经发出即预留一席。员工具备资格并激活后，同一席位计入已启用。核对时点击「刷新订阅与席位」，查看已启用、邀请预留和可用数量。试点尚未开通或可用席位用完时，本次创建会被拒绝。客户端会清除手机号和上一次邀请码，重新核对邀请权限，再显示本次拒绝原因及仍可查看的记录。

如果客户端提示「邀请已创建」且列表暂未刷新，请先核对并复制本次邀请码，再点「回首页刷新并清除邀请码」。刷新只读取邀请记录。列表恢复前，创建、撤销和翻页均锁定。关闭面板、切换团队或退出会清除显示的邀请码。若创建结果未确认，恢复连接后先核对邀请记录及预留席位。

| 身份 | 本轮可做 | 审计资料权限来源 |
|---|---|---|
| 开通审核员 | 录入、审核、撤销未用首管理员凭据 | 开通授权不附带资料权限 |

“团队名称”仅为显示名称，最长80个规范化字符，不证明企业资质。UI沿用现有品牌，只扩展必要操作；整体视觉升级仍在后续阶段。

## 服务端边界

- 开通权独立保存在 `team_platform_reviewers`，没有公开自助授予接口。客户端角色、身份头、普通经理或合伙人均不能充当审核事实；低职级或停用业务成员误授技术权仍拒绝。
- 审核须当前有效会话、当前密码和申请 revision；异步读 body/密码计算后重查同一操作者及授权。并发审批只有一个成功，动作写入不含秘密的事件表。
- 首管理员票仅存 SHA-256 哈希。票据绑定指定手机号、申请、批准者及批准时授权/密码版本。批准者正常退出不废票；批准者停用、撤权、版本变化、票据撤销/过期/已消费均拒绝。
- 专用 `first-admin` 验证码使用服务端随机数和 HMAC，绑定申请/手机号/用途/期限，5分钟、最多5次尝试；全局与手机号限流与既有SMS流程共享。SMS发送异步返回后重查票据和授权，失败不把挑战标成已发送。
- 激活须明确接受，不自动合并到第二个团队，不复活停用账号。已有任何业务或技术归属都拒绝再次激活；这是保守实验策略，多团队、移交和恢复规则尚待产品决定。
- 激活事务包含新账号（如需）、已验证手机号、团队、显示名称、独立 operator、申请和挑战消费、事件。任一SQL失败全部回滚，不发会话、不添加业务 membership、任务/项目/附件/平台管理 grant。
- 技术管理员员工邀请用独立来源表及对应挑战表，避免为满足旧邀请的成员外键而伪造审计职级。原业务邀请继续要求原经理/合伙人权限；技术授权不会使已失效业务票复活。两个来源遇到歧义默认拒绝。
- 列表每页最多 50 条，仅返回必要字段及遮罩手机号。开通票和验证码不进入列表或日志。访问审计数据仍走原授权，技术管理员直访本人或其他团队采集 API 均返回 404。

当前24小时邀请码和验证码限额是合成实验参数，未替用户决定最终商务/恢复政策。已批准但过期的记录仍显示“已批准，待本人激活”，同时显示有效期；实际预览/激活拒绝。丢失凭据需撤销后新录申请，没有重取明文接口；已激活申请不能用撤销票据操作删除团队。

### 新团队的首份采集

1. 由产品负责人按试点人员批准相应席位。走查使用两席，技术管理员邀请一位助理和一位实习生，两人各自激活并绑定设备。管理员在「员工业务职级」核对目标人员，验证当前密码并把该助理调整为项目经理。
2. 项目经理用本人账号登录，在「项目采集与资料核对」新建采集工作区，按职责勾选查阅、分工和核对，并验证当前密码。创建采集任务后，从任务行打开分工，搜索并选择已启用的实习生，确认指派。
3. 实习生从个人任务列表打开获指派的任务，选择文件并提交。经理从该项目的任务行点击「选择资料核对」，打开提交原件的只读预览，核对文件名、正文和摘要。任务保持已提交状态，后续专业审核按已批准流程办理。

### 试点审批的键盘操作

用 Tab 移到目标申请的截止时间和员工席位。日期各分段按控件顺序填写，截止时间按界面所示北京时间解释。填写审核账号当前密码后，移到该申请的「批准试点」，按 Enter 或空格明确提交。在密码框直接按 Enter 不会提交审核。

如果提交前焦点停在「批准试点」，服务端明确拒绝后，应用清空密码并把焦点放回密码框，保留原截止日期和席位。等待回执时已经用键盘转到其他控件的，应用会尊重原焦点顺序。收到结果未确认的提示时先刷新审核记录核对。

合成 Windows 走查完成 100% 与 200% 布局核对，日期、席位、密码、错误恢复与成功审批在 200% 下以键盘验证。 [验收状态](STATUS.md#2026-11-19-m8q-windows-试点审批键盘与缩放)

### 试点到期时

试点到期以服务端记录的结束时刻为准。技术管理员可刷新「订阅与席位」查看“团队试点 · 已到期”。此时再发邀请会收到订阅状态提示。项目经理的新建任务停止，应用提示联系团队管理员核对期限。原有项目权限仍用于查阅历史、预览提交和导出已选原件。到期本身不使已登录、仍有效的设备会话退出。

在 Windows 隔离受管服务中，以短时合成试点跨越实际结束时刻。两类写入各一次返回 402，已授权历史的原件和已有业务、权益记录通过独立只读核对。正式续费和商户收款按上线验收办理。 [验收状态](STATUS.md#2026-11-19-m8o-windows-受管试点自然到期)
