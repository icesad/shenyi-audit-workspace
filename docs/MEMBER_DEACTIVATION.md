# 团队成员停用

2026-11-15；M2本机合成候选。详细执行与验收边界见[合同](MEMBER_DEACTIVATION_CONTRACT.md)。

技术管理员可停用本团队的实习生、助理、项目经理和合伙人。技术管理员身份只能由具有独立 `member.disable` 授权的产品负责人处理。审计职级、邀请权、团队开通审核权和恢复密码审核权都不自动获得停用权限；管理员也不能在普通成员入口停用自己或其他管理员。

登录后，获授权人员使用“团队成员停用”面板。团队管理员只选择服务端返回的本团队；产品负责人可以切换到管理员身份列表。按姓名搜索、选择明确对象，再输入本人当前密码确认。名单仅提供完成停用所需的姓名、身份、团队、账号状态和版本，不提供手机号、项目结构或原件。错误密码可重试；状态或授权变化要求刷新；网络结果不确定时先刷新核对，不自动重发。

停用在同一事务中完成：账号不可登录、旧会话全部撤销、该团队任务指派及项目/附件/邀请权限失效，相关未完成的短信、恢复和微信授权流程也失效。有效指派涉及的任务各递增一次版本，旧分工页面不能继续使用原版本写入。账号、手机号/微信绑定、凭据、已接受邀请、任务状态、原件及提交历史保留，并新增明确记录操作者与目标的专用审计事件。任何步骤失败均回滚，避免只停一部分权限。

已打开的员工窗口在下一次服务请求时收到401并清空当前账号和任务资料；原件保存窗口尚未完成时也会重新核权，拒绝继续落盘。没有远程删除此前合法副本的功能，也不承诺跨网络核权与本地IO完全原子。

当前候选只处理所有历史归属都在同一团队的账号。具有其他团队历史、其他特权审核身份或不安全版本状态的对象，不能在此入口停用，以免误伤其他授权范围。停用后的重新启用、恢复原权限、多团队及所有权移交不在本轮实现范围，需分别明确规则。原角色和历史记录不会被删除或改成其他身份。

桌面新增5项窄操作，总54项，10个form、16个密码输入；没有通用网络、文件路径或授权参数接口。新schema只追加 `team_access_reviewers`、`team_member_access_events` 及3个身份epoch触发器；原39表及20个恢复epoch触发器不改，升级后41表、67个schema对象。服务端每次按当前事实授权，body读取、密码KDF后及事务内都复核同一账号、权源、凭据和目标版本，防止并发与撤权后同值重授。
