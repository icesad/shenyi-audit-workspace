# 正式身份方向：手机号密码＋微信扫码

日期：2026-11-15；来源：用户对正式账号选项回复“2加上微信扫码登录？”；按“手机号＋密码，并增加微信扫码登录”落实为产品方向。当前本机用户名演示账号仅作测试，不冒充正式手机号验证或微信接入。

## 1. 同一个员工账号，两种登录方式

服务端内部User ID不随手机号或微信身份变化，团队/角色/项目/设备/席位都关联该内部ID。手机号验证成功后建立手机号凭据；微信通过可信授权关联同一个内部ID。登录成功不意味着自动加入团队、获得合伙人或获得付费席位。

不能按微信昵称、头像、客户端提交的手机号或未经证实的UnionID自动合并用户。手机号换绑/微信绑定解绑/账号恢复都需当前强认证及必要的短信验证，记录审计事件，并按风险撤销旧会话；旧手机号不能自动取得后来持有者的客户权限。

## 2. 手机号＋密码

- 生产手机号规范化为统一表示，服务端短信挑战绑定操作用途和账号；短期、单次、次数限制、防重放，发送频率和验证错误限额分别控制。
- 注册/激活、登录、找回、换绑分别设计；不把“发送成功”当成已验证，也不在真实供应商不可用时返回虚假成功。
- 密码沿用成熟自适应哈希和服务端会话机制，不明文保存；日志不含验证码、口令、令牌、原件或完整手机号。
- 短信提供商、签名、模板、计费、实际发送及主体资质未具备前，只能用明确的测试适配器和合成号码验协议；不能向真实号码发送或声称真实验证通过。
- 管理员邀请不能设置被邀请人的正式永久密码；团队邀请、账号验证与职级授权分别完成。

## 3. Windows/Mac的微信扫码方案（候选设计）

`桌面创建短期登录事务 → 系统浏览器打开官网登录页 → 微信扫码授权 → 国内HTTPS回调 → 服务端校验state并换取微信身份 → 已绑定账号登录或首次强验证关联手机号 → 发起桌面实例单次兑换 → 审易会话 → 团队/任务/设备/订阅检查`。

- 通过微信开放平台的适用网站应用能力接入，不将公众号、小程序OpenID或微信支付商户身份直接混用。
- 原生桌面优先借助系统浏览器授权。当前桌面严格禁止任意外链；实现时只为本产品已核验的认证域名提供窄的系统浏览器入口，不开放通用`openExternal`或放宽renderer网络。
- AppSecret和微信令牌留在国内服务端；renderer、安装包、Git和日志不含这些秘密。客户端不能拿AppSecret直接换用户身份。
- 随机`state`绑定账号登录事务、有效期和最初客户端；微信code仅一次交换，回调和桌面兑换都防重放。桌面自己的兑换层可采用nonce/PKCE等证明，不能假定微信接口本身支持PKCE。
- 微信身份键以`(appId,openid)`区分；UnionID是否返回及跨应用关联条件按实际官方权限和真实响应验证，不能把它当始终存在。
- 首次微信授权不等于已验证手机号。建议首次扫码需对现有员工账号重新认证并验证手机号，再明确确认关联；同一手机号已有账户时不能静默覆盖绑定。
- 扫码取消、过期、用户未绑定、手机号冲突、两端并发、旧账号解绑、服务端撤销和异常回调都要有可恢复状态；缺少配置时展示真实未开通状态，不放一个总返回成功的二维码。

## 4. 外部前置与权限

经营主体/省份确认 → 域名实名和国内部署/HTTPS回调 → 核对微信开放平台认证及网站应用审核条件 → 获取相应应用ID与服务端凭据 → 短信主体签名/模板和服务开通 → 隔离测试 → 真实授权联调与验收。

截至本次仍无域名、服务器、短信供应商或微信应用资料。不得代购、代签、自动申请或索要明文密钥；所需费用/审核周期按实际官方申请页面核对，不预先保证个人主体可申请或给固定收费日程。微信登录与微信支付是两个独立接入，不因其中一个获批就声称另一项可用。

## 5. 测试和完成边界

先实现可替换的手机号/SMS与微信身份适配器契约及合成端到端测试；测试中模拟供应商必须显式标注。覆盖验证码用途/期限/次数/单次性、限流、手机号重复和换绑、OAuth state/code/桌面凭据重放、错误AppID、取消/超时、账号关联冒领、设备及团队权限不随登录方式提升。

只有真实短信签名/模板、微信应用审核/配置、真实授权回调、Win/Mac系统浏览器回到桌面、绑定和退出/撤销分别有证据，才可称对应生产能力验收；本机用户名密码流程不算这些关卡通过。
