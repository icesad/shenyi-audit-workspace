# 采集任务指派与退回

日期：2026-11-15；M2本机隔离候选。桌面已接任务管理，沿用用户确认的范围：获项目采集管理权的经理/合伙人，只能把任务指派给本团队有效实习生或助理。技术管理员、业务职级或邀请权本身不附带任务管理权。

## 操作流程

1. 使用获授权的经理/合伙人账号登录，在已有可读采集任务中选择任务。服务端确认该项目 `collection.manage` 后，详情显示“任务分工与退回”；不展示完整项目或资料结构。
2. 按姓名查找并选择本团队实习生/助理，点击“确认改派并替换当前分工”。这是单目标替换当前有效分工，不是追加多人共同分工；界面明确提示。候选仅姓名、职级和用于操作的内部ID，不包含手机号、凭据或业务数据。
3. 改派立即影响后续服务端访问：原低权限采集员失去任务、提交历史及下载访问，新人可见任务，但不会继承旧原件的附件授权。既有原件、提交记录、UUID和hash保持，不删除或覆盖。
4. 改派本身不改变提交状态。已提交任务仍为“已提交”；若需新人补充，管理者先点击“退回补充资料”，任务变“待补充”，采集员才能重交。
5. 每次改派、提交和退回都递增同一任务版本。若别人已经更新，旧页面操作409且锁定写入，必须“重新读取分工”后核对；不会自动重发操作或覆盖新提交。

退回是资料采集协作，不产生专业审计结论、审批签发或自动原件共享。管理者的“我的提交记录”仍只显示其本人提交；`collection.manage`不会自动让其读取员工提交摘要、原件或下载。已合法保存到本机的副本不能保证远程删除。

## 权限与接口

条件是当前任务可读、当前manager/partner、该任务所属项目有active `collection.manage` 的交集。低职级误授grant仍拒绝；技术operator无审计membership不能访问任务。冻结项目/关闭任务不提供管理能力或写入。目标必须同团队、账号/成员有效且role为intern/assistant；不能直接传另一个角色或其他团队用户ID绕过名单。

| 操作 | API | 关键边界 |
|---|---|---|
| 管理能力与当前分工 | `GET /api/teams/:teamId/collection/tasks/:taskId/management` | 不可管理仅`{canManage:false}`，无人员资料；有权才返回版本、状态及最多50当前分工/截断标记 |
| 可指派候选 | `GET`同task`/assignees` | SQL授权/active/角色过滤先于搜索和分页，默认20最多50、稳定ID游标，未知/跨范围游标同404 |
| 改派 | `POST`同task`/assignment` | 精确body`{userId,revision}`，一次递增，禁止无版本旧调用 |
| 退回 | `POST`同task`/return` | 精确body`{revision}`，仅submitted可退回，一次递增 |

管理写在读取body后、事务内都重新确认同一操作者及当前权限/项目/成员/版本。并发一个成功；任务状态、分工、版本与活动事件同事务，SQL失败全部回滚。上传的同账号检查也补齐；原上传版本合同保留，没有新增数据库表或改动存储语义。

桌面新增 `getTaskManagement`、`listTaskAssignees`、`assignTask`、`returnTask`，共48个窄IPC，仍9个form/15个密码输入。仅固定URL/参数/返回白名单，token留main。权限状态来自服务端，任务/团队/账号切换丢弃迟到结果；跨刷新写锁保留，不确定结果提示核对，不假称取消或回滚，不自动重试。
