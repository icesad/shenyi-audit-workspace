# 已确认工作区的资料清单接入

资料现在区分两个身份：团队工作区 W 用于权限、任务、路径和服务端存储；原业务身份 Q 保留在专业资料包和清单内容中。完成负责人业务确认后，可以按原五项独立资料权限接入对应 Q 的资料，不需要重命名 UUID 或改写旧包。

## 正常操作

1. 经理／合伙人正常创建采集工作区，明确选择采集权限，并按现有流程分派任务、收集原件。
2. 项目负责人核验已保存的中标／立项来源并验证密码，完成 W 与 Q 的正式业务确认。该确认不是审计签发，也不自动授予资料权限。
3. 负责人在资料权限配置中，验证当前密码后，逐项授予自己或本项目合格经理／合伙人 read、import、review、close、maintain。后四项依赖 read，维护还绑定当前 read 授权代次。
4. 获 read＋import 的用户选择原 Q 的正式资料保全包。预检核对目标工作区 W、原业务 Q、原名称、包 SHA、全部历史及原件；明确确认并输入密码后导入。现存资料不能覆盖。
5. 获 read 的用户可以发现 W 并查看该清单及全部历史原件。只有资料权的用户不会因此取得采集任务读取、管理或核对权。
6. 核对、关门／重开和原件维护分别遵守 review、close、maintain。closed 禁止核对／维护，须获 close 者说明理由和验证密码后重开；维护会按原规则重置相关叶的核对状态。

工作区列表仍使用 W；清单与来源说明展示原业务 Q。即使 W 与 Q 恰好相同，也按已确认工作区的明确身份处理，不按字符串相同推断旧项目。

## 原始资料与历史

原包不改 ID，不移动、覆盖或重新编号原件。首次导入的 source record、包 SHA、原版本和导入事实保持；原件 UUID、元数据、字节和历史仍全部保留。后续只有原模型允许的核对／关门／重开／新增／移除关联操作，继续保留 Q。

采集任务原件不会自动并入专业资料清单。资料 read 包含本清单历史原件的受限预览与按权限保存，不能据此读取其他项目或其他模块。

立项来源 JSON 的 SHA 与资料 ZIP 的 SHA 分别核验；它们不是同一工件。Q 一致和包完整性不能证明现实中标、实时最新状态或专业签发，历史姓名也不会自动变成认证员工账号。

## 断网、失权和未知结果

断网暂停业务。导入或资料动作可能已提交但回复丢失时，保留原查询编号；正常恢复设备会话后只读查询原回执，不自动重放。暂时查询不到也不能据此断定在途请求永远不会完成。

权限、账号、设备、项目或版本变化会阻止后续交付。预览在交付边界复核身份，打开后按原周期核权；保存仍在 Save 返回后 fresh 检查并原子发布，失权时不截断已有目标。取消或关闭只清理本次私有来源，不伪称撤回已提交的业务。
